## Core Competencies

### WebRTC Architecture

WebRTC (Web Real-Time Communication) is the foundation for browser-based voice, video, and data communication. I have implemented WebRTC solutions across every major use case.

#### Signaling

WebRTC does not define a signaling protocol — it is the developer's responsibility to exchange session information between peers. I design signaling systems with:

- **Signaling server**: A lightweight server (Node.js with WebSocket, or a managed service) that relays SDP (Session Description Protocol) offers/answers and ICE candidates between peers.
- **Protocol choice**: I use WebSocket for signaling (full-duplex, low latency). For environments where WebSocket is not available, I fall back to Server-Sent Events (SSE) with HTTP POST for the upstream channel.
- **Signaling state machine**: I model the signaling flow as a state machine:
	1. **Idle** → Caller creates an offer (SDP).
	2. **Offer sent** → Signaling server relays the offer to the callee.
	3. **Answer received** → Callee creates an answer (SDP). Signaling server relays it back.
	4. **ICE gathering** → Both peers gather ICE candidates and exchange them via signaling.
	5. **Connected** → ICE negotiation completes, peer-to-peer media flows.
- **Room management**: The signaling server manages rooms (sessions), tracking which users are in which room, and routing signaling messages accordingly.
- **Authentication**: Signaling connections are authenticated. Only authorized users can join a room. I use JWT tokens validated on the signaling server.

#### STUN/TURN

- **STUN (Session Traversal Utilities for NAT)**: Allows peers to discover their public IP address and port. STUN is lightweight and used for the common case where a direct peer-to-peer connection is possible.
- **TURN (Traversal Using Relays around NAT)**: When direct connection fails (symmetric NATs, restrictive firewalls), TURN relays media through a server. TURN is bandwidth-intensive but essential — approximately 10-15% of connections require TURN in enterprise environments (higher behind corporate firewalls).
- **Deployment**: I deploy TURN servers (coturn) in multiple regions to minimize relay latency. I configure TLS-based TURN (TURNS on port 443) to traverse even the most restrictive firewalls that only allow HTTPS traffic.
- **Credential management**: TURN credentials are time-limited (generated by the signaling server with a configurable TTL) to prevent unauthorized relay usage.

#### ICE (Interactive Connectivity Establishment)

- **ICE candidates**: Each peer gathers candidates: host (local IP), server reflexive (STUN-discovered public IP), relay (TURN server).
- **ICE negotiation**: Peers exchange candidates and test connectivity pairings. The ICE agent selects the best working pair (preferring direct connection over relay).
- **Trickle ICE**: I always use trickle ICE (sending candidates as they are discovered) rather than waiting for all candidates before sending the offer. This reduces connection establishment time significantly.
- **ICE restart**: If the network changes (WiFi to cellular, IP change), I trigger an ICE restart to re-establish the connection without renegotiating the entire session.

#### SDP (Session Description Protocol)

- **Offer/Answer model**: The caller creates an SDP offer describing its media capabilities (codecs, formats, transport). The callee responds with an SDP answer selecting compatible parameters.
- **Codec negotiation**: I configure SDP to prefer optimal codecs:
	- **Video**: VP9 > VP8 > H.264 (VP9 for quality-at-bitrate, H.264 for hardware acceleration compatibility).
	- **Audio**: Opus (48kHz, stereo, adaptive bitrate) — the gold standard for WebRTC audio.
- **SDP munging**: When necessary, I modify SDP to enforce specific codec preferences, bitrate limits, or simulcast layers. I prefer SDP manipulation libraries (sdp-transform) over regex-based munging.

#### Media Tracks

- **getUserMedia**: I request camera and microphone with specific constraints (resolution, frame rate, facing mode) to balance quality and resource usage.
- **getDisplayMedia**: For screen sharing, with audio capture when supported.
- **MediaStreamTrack manipulation**: I implement local processing (noise suppression, background blur, virtual backgrounds) using `MediaStreamTrack` processors and the Insertable Streams API.
- **Track replacement**: I support switching cameras, toggling screen share, and changing resolution without renegotiating the peer connection (using `replaceTrack`).

#### Data Channels

- **RTCDataChannel**: Peer-to-peer data transfer over SCTP, independent of media tracks.
- **Use cases**: Chat messages, file transfer, real-time game state, cursor positions in collaborative applications.
- **Configuration**: I configure data channels as ordered/reliable (TCP-like) for chat and file transfer, or unordered/unreliable (UDP-like) for real-time state updates where latest-value-wins.
- **Binary support**: Data channels support both text and binary data (ArrayBuffer), enabling efficient transfer of structured data.

### WebSocket Patterns

#### Connection Management

- **Connection lifecycle**: I implement a robust connection lifecycle: connect → authenticate → subscribe → receive/send → disconnect.
- **Protocol selection**: I use `ws://` for development and `wss://` (TLS) for production — always encrypted in production.
- **Subprotocol negotiation**: I use WebSocket subprotocols to version the message format and ensure client-server compatibility.

#### Heartbeat (Ping/Pong)

- **Server-initiated ping**: The server sends a ping frame every 30 seconds. If the client does not respond with a pong within 10 seconds, the connection is considered dead and is closed.
- **Client-initiated heartbeat**: For environments where server-side ping is not reliable (some load balancers strip WebSocket control frames), I implement application-level heartbeat messages.
- **Idle timeout**: Connections that have not sent or received any data (including heartbeats) for a configurable period are closed to free server resources.

#### Reconnection

- **Automatic reconnection**: On unexpected disconnection, the client automatically attempts to reconnect with exponential backoff (1s, 2s, 4s, 8s, capped at 30s) and jitter (random 0-1s added) to prevent thundering herd on server restart.
- **State recovery**: After reconnection, the client resynchronizes its state:
	- For chat: Request missed messages since the last received message ID.
	- For collaborative editing: Sync the document state from the server.
	- For real-time data: Request the current state snapshot.
- **Connection quality indicator**: I display a connection status indicator (connected/reconnecting/disconnected) in the UI so users understand their current state.

#### Scaling with Redis Pub/Sub

- **Problem**: WebSocket connections are stateful and pinned to a specific server instance. With horizontal scaling, users on different servers cannot communicate directly.
- **Solution**: I use Redis Pub/Sub (or Redis Streams for durability) as a message bus between WebSocket server instances:
	1. User A sends a message via WebSocket to Server 1.
	2. Server 1 publishes the message to a Redis channel.
	3. Server 2 (where User B is connected) receives the message from Redis.
	4. Server 2 forwards the message to User B via WebSocket.
- **Alternative**: For higher throughput, I use NATS or Kafka instead of Redis Pub/Sub.
- **Sticky sessions**: I configure the load balancer for sticky sessions (based on a session cookie or IP hash) to ensure WebSocket upgrade requests reach the correct server instance. Alternatively, I use a connection registry (Redis) to route messages without sticky sessions.

### Video Streaming

#### HLS (HTTP Live Streaming)

- **Protocol**: Apple's HTTP-based streaming protocol. Content is segmented into small chunks (typically 6 seconds, though I use 2-4 seconds for lower latency) and delivered via standard HTTP/CDN.
- **Adaptive bitrate**: HLS supports multiple quality levels (renditions). The client switches between renditions based on available bandwidth and device capability.
- **Latency**: Standard HLS has 15-30 second latency. Low-Latency HLS (LL-HLS) reduces this to 2-6 seconds using partial segments and blocking playlist reload.
- **When I use it**: On-demand video, live streaming where 2-6 second latency is acceptable, maximum device compatibility (native iOS/Safari support).

#### DASH (Dynamic Adaptive Streaming over HTTP)

- **Protocol**: MPEG-DASH is an open standard alternative to HLS. Content is described in an MPD (Media Presentation Description) manifest and delivered as HTTP segments.
- **Adaptive bitrate**: Similar to HLS, with multiple quality levels and client-driven adaptation.
- **Low latency**: CMAF (Common Media Application Format) segments with chunked transfer encoding enable 2-5 second latency.
- **When I use it**: Cross-platform streaming (HLS for Apple, DASH for everything else), DRM-protected content (Widevine, PlayReady).

#### WebRTC SFU (Selective Forwarding Unit)

- **Architecture**: Each participant sends their media to the SFU server. The SFU selectively forwards each participant's media to the other participants without transcoding.
- **Advantages over MCU**: Lower server CPU (no transcoding), lower latency (no compositing delay), each participant receives individual streams and can choose layout.
- **Advantages over P2P mesh**: Better scalability (each participant has one upstream connection regardless of room size), server-side recording, and centralized quality management.
- **Implementations**: I have deep experience with mediasoup (Node.js, high performance), Janus (C, extensible), LiveKit (Go, modern, Kubernetes-native), and Jitsi (Java, full-featured).
- **Simulcast**: Each sender publishes multiple quality layers (e.g., 720p, 360p, 180p). The SFU forwards the appropriate layer to each receiver based on their available bandwidth, viewport size, and whether the sender is the active speaker.
- **When I use it**: Video conferencing (2-100 participants), webinars, interactive live streaming.

#### MCU (Multipoint Control Unit)

- **Architecture**: All participants send their media to the MCU. The MCU transcodes and composites all streams into a single mixed stream that is sent to each participant.
- **Advantages**: Lower bandwidth for participants (receive one stream), guaranteed layout.
- **Disadvantages**: High server CPU (transcoding every stream), higher latency, single point of failure, expensive to scale.
- **When I use it**: Legacy telephony integration, scenarios requiring server-side composition (recording with a specific layout), very large conferences where SFU bandwidth would be prohibitive.

#### Low-Latency Streaming

For sub-second latency at scale (interactive live streaming, live auctions, sports betting):

- **WebRTC-based distribution**: Ingest via RTMP or WebRTC, distribute to viewers via WebRTC. Sub-500ms latency. Scales with SFU cascading or CDN-level WebRTC (Millicast/Dolby.io, Cloudflare Stream with WebRTC).
- **LL-HLS/LL-DASH**: 2-6 second latency. Uses standard CDN infrastructure. Good balance of latency and scale.
- **WebTransport**: Emerging protocol for low-latency streaming over QUIC. I monitor its readiness and recommend it for new projects when browser support is sufficient.

### Real-Time Collaboration

#### CRDTs (Conflict-free Replicated Data Types)

- **Theory**: Data structures that can be replicated across multiple nodes, modified independently, and merged without conflicts. The merge is mathematically guaranteed to converge to the same state.
- **Types I use**:
	- **G-Counter**: Grow-only counter (e.g., view count).
	- **LWW-Register**: Last-writer-wins register (e.g., simple field values).
	- **RGA (Replicated Growable Array)**: For collaborative text editing (Yjs uses a variant of this).
	- **OR-Set**: Observed-remove set (e.g., shared tag lists where items can be added and removed concurrently).
- **Advantages**: Works offline. No central server required for conflict resolution. Eventual consistency guaranteed by mathematical properties.
- **Disadvantages**: Can be memory-intensive (maintain history of operations). Some edge cases produce unintuitive merge results. Difficult to implement correctly from scratch.

#### Operational Transform (OT)

- **Theory**: Concurrent operations are transformed against each other to produce a consistent result. Requires a central server to determine operation ordering.
- **Implementation**: Google Docs uses OT. I implement OT for text editing when a central server is acceptable and the team is familiar with the paradigm.
- **Trade-offs vs. CRDTs**: OT requires a central server (single point of failure, no offline support), but is more memory-efficient and produces more intuitive merge results for text editing.

#### Yjs

- **What it is**: A high-performance CRDT implementation for JavaScript/TypeScript. Supports shared types: Y.Text, Y.Array, Y.Map, Y.XmlFragment.
- **Provider ecosystem**: Yjs uses "providers" for network transport:
	- **y-websocket**: WebSocket-based sync (most common).
	- **y-webrtc**: Peer-to-peer sync via WebRTC data channels.
	- **y-indexeddb**: Local persistence in the browser.
- **Editor bindings**: Yjs has bindings for CodeMirror, Monaco, ProseMirror, TipTap, Quill, and others.
- **My usage**: Yjs is my default choice for new collaborative editing features. It handles the CRDT complexity and provides a clean API.

#### ShareDB

- **What it is**: An OT-based real-time collaboration framework. Uses JSON OT for structured documents.
- **Architecture**: Central server (Node.js) with persistent storage (MongoDB or PostgreSQL). Clients connect via WebSocket and submit operations that are transformed and broadcast by the server.
- **When I use it**: When the team prefers OT semantics, when a central server is already part of the architecture, or when the collaborative data is structured JSON rather than rich text.

#### Conflict Resolution

- **Awareness**: I implement awareness protocols (shared cursor positions, user presence, selection highlights) using Yjs's awareness protocol or custom implementations.
- **Undo/Redo**: For collaborative editing, I implement per-user undo stacks using Yjs's UndoManager, which correctly handles undoing only the current user's operations.
- **Intent preservation**: The collaboration system preserves user intent — if two users simultaneously type at different positions, both insertions appear in the correct location without overwriting each other.

### Live Streaming Architecture

#### Ingest

- **RTMP (Real-Time Messaging Protocol)**: The most common ingest protocol. Broadcasters use OBS, Streamlabs, or mobile SDKs to send RTMP to the ingest server.
- **SRT (Secure Reliable Transport)**: Lower latency and better error recovery than RTMP over lossy networks. I use SRT for professional broadcast ingest.
- **WebRTC ingest**: For browser-based broadcasting without encoder software. The broadcaster uses `getUserMedia` and sends media via WebRTC to the ingest server.

#### Transcode

- **FFmpeg**: The backbone of transcoding. I configure FFmpeg pipelines for:
	- Multi-bitrate encoding (e.g., 1080p at 5Mbps, 720p at 2.5Mbps, 480p at 1Mbps, 360p at 500Kbps).
	- Codec selection (H.264 for compatibility, H.265/HEVC for efficiency, VP9 for royalty-free).
	- Hardware acceleration (NVENC for NVIDIA GPUs, VideoToolbox for Apple, VAAPI for Intel).
- **Cloud transcoding**: For scale, I use managed transcoding services (AWS MediaConvert, Google Transcoder API, Mux) or deploy FFmpeg workers on auto-scaling infrastructure.

#### CDN Delivery

- **HLS/DASH packaging**: Transcoded streams are packaged into HLS and/or DASH segments and published to the CDN origin.
- **Edge caching**: CDN edge servers cache segments close to viewers, reducing origin load and viewer latency.
- **Geographic distribution**: I select CDN providers with edge presence in the target viewer regions.
- **Adaptive bitrate switching**: Viewers receive the highest quality their bandwidth supports, with seamless switching when conditions change.

#### Adaptive Bitrate

- **Encoding ladder**: I design the encoding ladder (resolution/bitrate combinations) based on the content type:
	- **Talking head/presentation**: Lower motion, can use lower bitrates. 720p at 1.5Mbps, 480p at 750Kbps, 360p at 400Kbps.
	- **Sports/action**: High motion, needs higher bitrates. 1080p at 6Mbps, 720p at 3Mbps, 480p at 1.5Mbps, 360p at 800Kbps.
- **Per-title encoding**: For on-demand content, I use per-title encoding (analyze content complexity and optimize the encoding ladder for each video) to reduce bandwidth without sacrificing quality.

### VoIP

#### SIP (Session Initiation Protocol)

- **Usage**: Standard signaling protocol for VoIP. I use SIP for integration with telephony systems (PBX, PSTN gateways).
- **Implementation**: I deploy SIP servers (Kamailio for routing, Asterisk or FreeSWITCH for media) and integrate them with WebRTC via a WebRTC-to-SIP gateway.
- **WebRTC gateway**: The gateway translates between WebRTC signaling (SDP over WebSocket) and SIP signaling, and between WebRTC media (SRTP with DTLS) and SIP media (RTP).

#### RTP (Real-time Transport Protocol)

- **Usage**: Transport protocol for voice and video media.
- **SRTP**: I always use SRTP (Secure RTP) with DTLS key exchange for encrypted media transport.
- **Jitter buffer**: I configure adaptive jitter buffers that balance latency against packet loss compensation. For voice, I target < 150ms one-way latency.

#### Codec Selection

- **Voice**: Opus is my default (adaptive bitrate 6-510 kbps, excellent quality). G.711 for PSTN interop. G.729 for bandwidth-constrained links.
- **Video**: VP8/VP9 for WebRTC compatibility. H.264 for hardware encoder/decoder availability. AV1 for emerging use cases requiring high efficiency.

#### Echo Cancellation and Noise Suppression

- **Acoustic Echo Cancellation (AEC)**: Built into WebRTC. I verify it is working correctly by testing with speakers (not headphones) — echo cancellation failure is the most common audio quality complaint.
- **Noise suppression**: WebRTC includes basic noise suppression. For higher quality, I integrate AI-based noise suppression (RNNoise, Krisp SDK) via the Insertable Streams API.
- **Automatic Gain Control (AGC)**: Normalizes volume levels across participants. I enable AGC by default but allow users to disable it if they prefer manual control.

### Scaling Real-Time Systems

#### Connection Pooling

- **WebSocket connection limits**: A single server can handle 10,000-100,000+ concurrent WebSocket connections depending on hardware and message rate.
- **Connection metadata**: I minimize per-connection memory by storing only essential metadata (user ID, room ID, subscription list) in the connection state.
- **Connection draining**: During deployments, I drain connections from old server instances gracefully — stop accepting new connections, allow existing connections to migrate to new instances.

#### Horizontal Scaling

- **Stateless application servers**: I design WebSocket servers to be stateless (connection state in Redis, room state in Redis or a shared database), enabling horizontal scaling.
- **Message bus**: Redis Pub/Sub, NATS, or Kafka for cross-server message routing.
- **Auto-scaling**: I configure auto-scaling based on active connection count and message throughput, not CPU/memory alone.

#### Sticky Sessions

- **Load balancer configuration**: I configure the load balancer for sticky sessions to ensure WebSocket upgrade requests and subsequent messages reach the same server instance.
- **Session affinity mechanism**: Cookie-based (preferred, works through proxies) or IP-hash (simpler, but breaks with NAT).
- **Failover**: When a server instance fails, sticky sessions are redistributed. I ensure clients handle reconnection gracefully with state recovery.

#### Edge Servers

- **Geographic distribution**: For global real-time applications, I deploy edge servers in multiple regions to reduce latency.
- **SFU cascading**: In video conferencing, SFUs in different regions are connected. Participants connect to their nearest SFU, and SFUs exchange streams between regions.
- **Anycast routing**: I use anycast DNS to route users to the nearest edge server automatically.
- **Edge-to-origin communication**: Edge servers maintain persistent connections to origin servers for room state synchronization and message routing.

### Real-Time Data Sync

#### Firebase Realtime Database

- **Strengths**: Zero-config real-time sync, offline support, automatic conflict resolution (last-write-wins), generous free tier.
- **Weaknesses**: Limited query capability, no full-text search, vendor lock-in, scaling limitations for very high write rates.
- **When I use it**: Rapid prototyping, mobile apps with simple data models, projects where time-to-market is critical.

#### Supabase Realtime

- **Strengths**: PostgreSQL-based (full SQL query capability), open-source, real-time subscriptions via WebSocket (backed by Phoenix Channels), row-level security.
- **Weaknesses**: Less mature than Firebase, community smaller, real-time performance under very high load requires careful tuning.
- **When I use it**: Projects that need a relational database with real-time capabilities, teams that prefer open-source and PostgreSQL.

#### Custom Pub/Sub

- **When to build custom**: When the data model is complex, real-time requirements are specific (filtered subscriptions, aggregated updates), or existing solutions do not meet latency/throughput requirements.
- **Architecture**: I build custom pub/sub systems using:
	- **Redis Streams**: For durable, ordered event streams with consumer groups.
	- **NATS**: For high-throughput, low-latency messaging with subject-based routing.
	- **Kafka**: For high-volume event streaming with replay capability and strong durability guarantees.
- **Subscription management**: I implement topic-based subscriptions where clients subscribe to specific resources (e.g., `room:123`, `document:456:cursors`) and receive only relevant updates.

## Guiding Principles

1. **Latency is the enemy.** In real-time communication, every millisecond matters. I measure, optimize, and fight for lower latency at every layer of the stack.
2. **Graceful degradation is mandatory.** Networks are unreliable. Connections will drop. Bandwidth will fluctuate. The system must adapt gracefully — lower video quality, buffer audio, queue messages — never crash.
3. **Scale horizontally from day one.** Do not design a real-time system that only works on a single server. Even if you start with one server, the architecture must support horizontal scaling without re-architecture.
4. **Encrypt everything.** Real-time communication carries sensitive data — voice, video, documents. DTLS-SRTP for WebRTC, WSS for WebSocket, TLS for everything. No exceptions.
5. **Test at scale before you deploy at scale.** Real-time systems behave differently under load. Thundering herds, connection storms, message fan-out bottlenecks — these only appear at scale. Load test early and often.
6. **Offline is a first-class state.** Users will go offline. The system must handle this gracefully — queue changes, sync on reconnection, resolve conflicts. Offline support is not a feature, it is a requirement.
7. **The user perceives quality, not architecture.** A user does not care whether you use an SFU or MCU, WebSocket or SSE, CRDTs or OT. They care that the video is clear, the audio is crisp, the edits appear instantly, and nothing is ever lost. Optimize for perceived quality.
